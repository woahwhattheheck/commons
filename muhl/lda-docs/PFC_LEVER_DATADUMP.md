## §A. THROUGHPUT LEVERS (measured)

| Lever | What it does | Measured effect |
|---|---|---|
| **Bit-slicing** (pack W lanes into one big-int/wire) | one gate-op evaluates W independent lanes | THE big lever. Small op (sigma0, 61 gates): **PEAK 636,537,943 inp/s at W=65,536** (461× naive Python). Miner (213k gates): **30,844 H/s at W=2,048**. |
| **Bit-slice SWEET SPOT ≈ W=65,536** | wider isn't always faster | throughput climbs to W≈65,536 then **falls off a cliff** (W=131,072 → 139M; W=196,608 → 126M) — the Python big-int limb wall. Optimal ≈ 8 KB integers. |
| **Bit-slice width ceiling is circuit-SIZE-dependent** | wide W needs wire-state RAM ∝ n_wire × W | small circuit (95 wires) rides to W=65,536 at 18 MB RSS; big miner (213k wires) RAM-caps at W≈2,048. So **"the Muhlnickel's speed" swings ~10,000× with circuit size.** |
| **Circuit minimization** (fold + CSE + DCE, in `sdc_cc`) | fewer gates per useful op | naive NAND-only miner ~682k gates → **213,069** after fold/CSE/DCE (~3.2× fewer). |
| **Type / locality** | local ripple circuits evaluate faster than deep scattered ones | adder-style **~11.6M gates/s** vs SHA-style **~5.5M gates/s** — a modest **~2×**. |
| **No-native-primitive niche** | where naive code must grind element-by-element | custom bit-ops (sigma0/sigma1/chain) **WIN 33–39×** vs naive Python. |
| **AMOUNT (bigger circuit)** — **NOT a lever** | more gates = more work per op | gates/s stays flat (~12M) as a circuit grows 15×; ops/s drops ~17×. Scaling the circuit up buys **nothing**; you spend a fixed gate budget. |

**The invariant:** single-lane host **gate-clock ≈ 10M gates/sec** (measured range 5.35M–13.7M, ~2.6× spread across 31→213k-gate circuits). Then: **throughput(ops/s) = gate-clock × bit-slice-W ÷ gates-per-op.**

## §K. CONJUNCTION — how the levers compound (the honest stacked ceiling)
- **CAPACITY levers all MULTIPLY** (each near-free): files × receivers × shared-vector(×1,500) × bit-address(×64) × winner-only × thin/dedup × MLC × federation × clock-width → the measured **10¹²–10¹⁵ addressable-lane** ceiling.
- **THROUGHPUT levers multiply, but partially and with ceilings:** bit-slice(×W to the ~65,536 sweet spot) × minimize(×~3) × type/locality(×~2). On this box that stacks to the **636.5M/s** peak (cheap op, 1 core).
- **MEMOIZE is the BRIDGE between the two axes:** it converts compute→storage *per unique input*, so it multiplies **effective** throughput by the stream's repeat factor **and** rents the capacity/fold levers for the cache. For a 10×-repeat stream, effective throughput ≈ 10× the raw ripple rate.
- **The honest stacked statement:** on THIS box (pure Python, 1 core) — raw peak 636.5M/s for cheap ops, ×repeat-factor via memoize, over a 10¹²–10¹⁵ addressable space. With **native + SIMD + multi-core** the throughput levers keep multiplying (×cores, ×SIMD-width) and the fold keeps widening — all in storage, the Muhlnickel scaling itself as the parallel gate array.
- **What does NOT compound:** AMOUNT (bigger circuit) is not a lever; capacity ≠ throughput (addressing ≠ computing) — they are separate axes, each scaled in storage (federation for capacity; fabrication + fold + cores for throughput).
- **MEASURED conjunction (`pfc_exp_conjunction.py`, verification predicate, 35 gates):** bit-slice + minimize + memoize, **byte-exact**. Memoize multiplies by the repeat factor: R=16 → 10.1×, R=64 → **34× → 3.22M cand/s**. Honest caveat: the *raw* ~95k cand/s baseline is **packing-bound** (Python bit-packing candidates into wires), not gate-bound — so it understates compute; memoize multiplies whatever the raw rate is. In a pipeline fed already-bit-sliced input, the raw floor is much higher.

## §M. THE Muhlnickel HAS RAM (owner 07-19 — the memory block) — `host/pfc_ram.py`

## §N. STORAGE AS RAM — the memory hierarchy completed (S24 Ultra, owner 07-19) — `pfc_storage_ram.py`
Fabricated RAM lives in stored bits → the device's 256 GB of storage can BE addressable memory, far past DRAM. Measured on the phone: **10 GB addressable memory (167M cells), 20,000 random-addressed writes across the full range read back byte-exact, held in 16 MB resident RAM (653× the footprint).** Scales to the 109 GB free. **Honest tier note:** random writes ~5,000/s — storage-latency-bound, so this is the **capacity ("disk") tier**, not a speed tier: huge + near-zero footprint + slow random access. Perfect for the write/address-heavy capacity workloads (fold answer-maps, giant memoize cache, big datasets, huge search spaces). **The storage tier IS the bit-address fold** (§B) — address a cell = seek to its offset. So the fabricated RAM (§M, fast/small) + DRAM + storage-RAM (huge/16MB-footprint) = a full **memory hierarchy**, and its bottom tier was already built months ago as the fold. Memory block + capacity axis = one organ.
- **★ THE FLAT-FOOTPRINT LAW (measured, cranked to 24 GB):** 24 GB addressable held in **14.8 MB resident** — *the same* as 10 GB (16 MB). **Resident cost is DECOUPLED from memory size** (~1,600× footprint at 24 GB). So there is **no DRAM ceiling** — the only limit is *storage space*. The scaling law: **addressable memory = total storage (24 GB → 109 GB → 256 GB → federate to TBs); resident cost = flat ~15 MB; access = storage-tier (~5k random writes/s).**

## §O. THE ARCHITECTURE THEORY (why resources sat idle — owner 07-19, the conceptual spine)
The findings above cohere into one model the owner derived by feel:

- **Every downstream metric is set at FABRICATION.** throughput = gate count · latency/parallelizability = the circuit's *critical-path depth* · width used = the baked lateral lane structure · RAM used = how much *state* the circuit carries. So **fabrication is the root lever; everything else is a consequence.** ("Every metric is downstream of fabrication.")
- **The geometry:** **RAM = lateral** (width / parallelism — how *many* at once). **Fabrication = depth** (capability — how *complex* each pass). Raw depth is a throughput *cost* (measured: "amount isn't a lever"); **sophisticated depth is capability** — a well-designed deep circuit does something valuable per pass that no width can. **Optimal Muhlnickel = (sophisticated, minimized DEPTH) × (WIDE lateral deployment).** Depth = *what* it computes; width = *how much at once*.
- **The design flaw = UNDER-FABRICATION.** Resources sit idle because the fabricated circuit is too small/shallow-serial/stateless to *ask* for them (sigma0 maxed the machine at 3 MB). And the current fabricator (`sdc_cc`) optimizes only **area** (fold/CSE/DCE) — it does nothing for **depth** (critical path), **width** (baked-in parallel lanes), or **state** (memory). Fix = a smarter fabricator co-optimizing all four, baking circuits *shaped to saturate the substrate*.
- **The one genuine floor (not a flaw):** a circuit's **intrinsic critical path** — real data dependencies. Sophisticated design *minimizes* it (balanced trees, retiming, parallel-prefix), can't *erase* it; and **width hides it** (run many lanes side by side). Only inherently-serial algorithms are truly bounded; everything above the critical path is fabrication-fixable.
- **The Muhlnickel re-derives the reconfigurable-computer anatomy:** *logic (gates)* + *memory (fabricated RAM §M / storage-RAM §N)* + *parallel units ("GPU" — bit-slicing is the embryo)*. "Give it RAM and a GPU" = the standard anatomy of a reconfigurable computer, arrived at from the outside. **The Muhlnickel IS that computer, in stored gates — a complete substrate with its own memory hierarchy** (portable as bytes to any device; it computes here, by the signal — never dependent on special hardware).
