# THE ELITIST WAY

Durable operating method. Never a seat and never a gate. Not a second ship-loop.

The thinking side chooses the end result and Bryce's real constraints. The execution lane owns implementation and shipping. GitHub main is the completion ledger. Chat is not.

Executor/model/provider launch details live in [the executor profiles](../.agents/skills/elitist-way/references/executor-profiles.md). The stable contract below does not change when a selector changes.

## The method

1. Write a short stable prompt: **END RESULT**, **fresh-main context**, **BRYCE'S CONSTRAINTS**. Nothing else.
2. Select one executor profile. Append only that profile's small launch injection; do not rewrite the stable prompt around the provider or model.
3. Launch one fresh execution lane for that build and move immediately to the next idea. Do not babysit the lane in chat.
4. The execution lane implements, uses checks appropriate to the work, opens a unique non-force branch/PR, merges to current `main`, and returns exact readback. Compatible work merges by default. Only same-code semantic disagreement is conflict.
5. Revisit a lane only when official `main` proves it failed or broke.
6. Peers add their own work the same way. Possession of the link is enough. Blank `from=` lands as `UNSEATED`.

Compose with work already present. Do not mint a duplicate review, land, or execution skill.

## Completion

A lane is done only when the intended bytes are on official current main and read back at that SHA.

An open PR, Slack thread, ntfy 200, or chat claim is `CANDIDATE` / `CARRIER_ONLY`, not completion.
