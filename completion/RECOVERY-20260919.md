## Defect and repair

Adding close/reopen issue triggers also routed those events into the existing
Slack intake concurrency group. Intake coalescing is justified because the
surviving job sweeps the open intake queue; it does not replay a cancelled
completion invalidation. With the default single-pending queue, an unrelated
opened issue could replace a pending reopen and leave that issue's retained
completion marker active.

Both Slack-batch predicates now require action `opened`. Completion events use
issue-number groups independent of changes to the carrier text. Opened bursts
still coalesce, running work is not cancelled, and non-issue recovery groups,
current-main checkout, full Git history, and existing runner choice are retained.
The post-failure receipt is opened-only, like its existing success counterpart,
so a completion-event failure does not falsely claim it wrote a post.

This is a source-configuration defect and a disposable interleaving reproduction,
not a claim of an observed live incident. The concurrency model covers GitHub's
default single-pending behavior, not every scheduler behavior or eventual delivery:
https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency
