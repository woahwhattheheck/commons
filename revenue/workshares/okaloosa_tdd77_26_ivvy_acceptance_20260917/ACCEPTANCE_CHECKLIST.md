# Okaloosa TDD 77-26 iVvy workshare — reviewer acceptance checklist

This checklist is an owner-review aid for the proposed Okaloosa TDD 77-26 specialist workshare. It does not create outbound, bidder, submission, contractual, production, payment, receivable, or revenue authority.

## Commercial / relationship gate

- [ ] A current Muse single-writer decision selects exactly one sender, route, offer, and purpose before any external outreach.
- [ ] Immediate Slack/Gmail/relationship recensus shows no competing writer, prior send, DNR, bounce/dead route, or human reply that changes posture.
- [ ] iVvy interest or an invitation to scope is evidenced before language implies a partner relationship.
- [ ] `$35,000 fixed / 15 business days` remains explicitly `PROPOSED_NOT_ACCEPTED` until counterparty evidence proves otherwise.
- [ ] No statement implies iVvy is bidding, qualified, selected, compliant with TDD 77-26, or obligated to use TJLabs without direct evidence.
- [ ] No statement implies Okaloosa County has accepted TJLabs, approved the workshare, or authorized a submission.

## Buyer / prime source gate

- [ ] The current official TDD 77-26 packet is supplied or authenticated by the prime/customer.
- [ ] Every controlling addendum and deadline change is included.
- [ ] The exact buyer naming and requirements for Workday, DocuSign, and BluePay/Bluepay are verified against the official packet rather than a secondary summary.
- [ ] The exact migration source/history requirement is verified against the official packet.
- [ ] Security/audit, support, training, hosted-provider, and other controlling requirements relevant to this slice are source-bound.
- [ ] Public iVvy product/API/integration claims are used only for topical fit; buyer-specific capability claims require prime/platform evidence.
- [ ] No public iVvy integration catalog is treated as proof that a native Workday, DocuSign, or BluePay connector exists.

## Scope freeze

- [ ] One TDD 77-26 workshare/slice id is recorded.
- [ ] Controlling RFP/addenda generation is recorded.
- [ ] Approved legacy source/export family and generation are recorded.
- [ ] Approved target export/read-only evidence family is recorded.
- [ ] Closed integration set is enumerated.
- [ ] Closed security/audit requirement set is enumerated.
- [ ] One rehearsal/cutover generation is named.
- [ ] Prime/customer acceptance decision owner is named.
- [ ] Data handling, redaction, transfer, and environment constraints are explicit.

## Evidence custody

- [ ] Every material source artifact has a stable evidence reference.
- [ ] Bytes under TJLabs custody have cryptographic digests recorded.
- [ ] Owner assertions are labeled as assertions rather than silently promoted to retained evidence.
- [ ] Screenshots, filenames, job-success banners, and operator statements are not treated as stronger evidence than they are.
- [ ] Missing, ambiguous, stale, or contradictory evidence yields HOLD rather than inferred PASS.
- [ ] Sampling rules are documented before sampled field-level checks are interpreted.

## Migration source profile / reconciliation

- [ ] Source generation identity is frozen.
- [ ] Population/object/file inventory is recorded where meaningful.
- [ ] Business/stable keys and approved remapping rules are explicit.
- [ ] Requiredness/type/transform rules used in acceptance are explicit.
- [ ] Attachment/document/reference handling is evidenced where relevant.
- [ ] Duplicate/orphan/unmapped/truncated/malformed rules are explicit.
- [ ] Source-to-target population and key reconciliation is complete for the admitted evidence.
- [ ] Historical gaps are explicit; requested history is not confused with available/validated history.
- [ ] Every agreed migration rule has `PASS`, `HOLD`, or `NOT_TESTABLE_FROM_SUPPLIED_EVIDENCE` with supporting evidence.

## Workday / DocuSign / BluePay integration acceptance

For every admitted buyer-named path:

- [ ] Source and target system owners are identified.
- [ ] Direction of flow is explicit.
- [ ] Business objects and identifiers are enumerated.
- [ ] Schema/semantic contract is explicit.
- [ ] Secret/authentication custody stays outside repository artifacts.
- [ ] Allowed environment and data class are explicit.
- [ ] Correlation/idempotency identity is defined where applicable.
- [ ] Retry/duplicate/reversal behavior is defined where applicable.
- [ ] Ordering/timezone assumptions that can affect outcomes are explicit.
- [ ] Positive and agreed negative-path evidence exists, or the case remains HOLD.
- [ ] Reconciliation depth is stated rather than implied.
- [ ] No destructive production replay occurred under this workshare.
- [ ] Native-connector availability is not inferred from iVvy's general API/integration catalog.

## Cutover rehearsal / rollback readiness

- [ ] Rehearsal source/target/evidence generations are frozen.
- [ ] Owner-controlled dependencies and preconditions are explicit.
- [ ] Observable checkpoints are enumerated.
- [ ] Owner-approved acceptance/reconciliation thresholds are recorded.
- [ ] Drift between rehearsal and final generation is checked or explicitly HOLD.
- [ ] Abort/HOLD triggers are explicit.
- [ ] Retry/re-run rules are explicit.
- [ ] Rollback prerequisites and owner decision points are explicit.
- [ ] No RTO/RPO, outage, rollback, or data-loss guarantee is invented by TJLabs.
- [ ] Go/no-go evidence separates proven facts from owner assertions and final owner authority.

## Security / audit acceptance

- [ ] Each admitted requirement maps to evidence or an explicit HOLD.
- [ ] Roles/access evidence is source-bound where required.
- [ ] Audit-event/log evidence is source-bound where required.
- [ ] Data-transfer and secret-handling evidence is source-bound where required.
- [ ] Retention/backup/incident evidence is included only when the controlling requirement calls for it and source evidence exists.
- [ ] Sensitive material follows owner-approved handling/transfer rules.
- [ ] No TJLabs artifact represents an independent SOC, PCI, legal, privacy, regulatory, or cybersecurity certification.

## Exception / HOLD ledger

For every finding:

- [ ] stable exception id;
- [ ] requirement/system/migration/integration reference;
- [ ] evidence references;
- [ ] observed result and expected result;
- [ ] owner-approved severity/disposition;
- [ ] responsible owner / next action;
- [ ] closure-evidence requirement;
- [ ] state is one of `OPEN`, `HOLD`, `RETEST_READY`, `CLOSED_WITH_EVIDENCE`.

No item disappears because the response or cutover deadline approaches.

## Final reviewer pack

- [ ] Frozen controlling-source/scope manifest is present.
- [ ] Evidence/digest inventory is present.
- [ ] Migration profile and reconciliation results are present.
- [ ] Integration acceptance contracts/matrices are present.
- [ ] Cutover/rehearsal readiness evidence is present.
- [ ] Security/audit requirements-to-evidence matrix is present.
- [ ] Exception/HOLD ledger is present.
- [ ] Retest/closure evidence is linked.
- [ ] Residual blockers are visible.
- [ ] Reviewer handoff separates proven facts, owner assertions, and unresolved items.
- [ ] Final language does not claim TJLabs is the bidder, platform authority, final architect, compliance certifier, buyer, signatory, submitter, production operator, or commercial acceptance authority.

## Delivery-complete decision

Delivery may be marked complete only when the bounded evidence product is complete and traceable. It does **not** require pretending owner-controlled HOLDs are resolved. Missing owner evidence/decisions remain explicit blockers.
