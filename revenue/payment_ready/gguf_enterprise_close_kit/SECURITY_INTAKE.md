# GGUF Diagnostic — Security / Data-Handling Intake

This questionnaire is the buyer-evaluable security boundary for `gguf-diagnostic-10d-12k`. Answers should be resolved before private file transfer. Public Commons records only the allowed metadata/receipt fields described below.

## Required customer confirmations

| Question | Required answer | If not satisfied |
| --- | --- | --- |
| Do you control the GGUF and have authority to provide it for this engagement? | Yes | `HOLD_GGUF_CONTROL` |
| Is the evaluation harness runnable before file transfer? | Yes | `HOLD_HARNESS_NOT_READY` |
| Can the harness command/config be frozen to an opaque SHA-256 identity? | Yes | `HOLD_HARNESS_NOT_READY` |
| Can the evaluation-suite identity be frozen to an opaque SHA-256? | Yes | `HOLD_HARNESS_NOT_READY` |
| Is the requested intervention bounded by the signed SOW? | Yes | `HOLD_CHANGE_ORDER` |
| Will private transfer occur outside Commons through the agreed owner-private channel? | Yes | `HOLD_OWNER_PRIVATE_EXTERNAL` |
| Can the customer keep credentials out of Commons and out of the diagnostic artifact bundle? | Yes | `HOLD_OWNER_PRIVATE_EXTERNAL` |
| Can the customer accept a hash/receipt-based evidence packet instead of public original/ablated/restored model binaries? | Yes | `HOLD_PRIVATE_DELIVERY_REQUIRED` |
| Is acceptance AT1–AT6 rollback evidence rather than guaranteed metric lift? | Yes | `HOLD_TERM_CONFLICT` |

## Data classes

### Allowed in Commons

- opaque engagement and customer reference IDs;
- SHA-256 digests of the GGUF, harness command/config, evaluation suite, run receipts, report, and delivery receipt;
- byte counts;
- non-secret tool/version labels;
- a public HTTPS contact URL with no query string or fragment;
- redacted objective/finding/limitations text;
- boolean readiness/control attestations; and
- non-secret deterministic receipts generated by the close-kit.

### Never in Commons

- GGUF or other model bytes;
- private evaluation prompts/cases/datasets;
- original/ablated/restored binary diffs that leak the diagnostic method;
- passwords, API keys, auth tokens, signing keys, or production credentials;
- signed NDA/SOW bytes or signature metadata beyond an opaque external receipt hash;
- card, bank, routing, account, tax, payout, or processor credential values;
- private buyer email/phone/address/contact data; or
- any secret placed inside a URL query string or fragment.

## Transfer boundary

The public `diagnostic.html` surface is purchase-intent only. It does not accept payment or model files. Private customer artifacts may move only after owner review of external NDA, SOW, and M1 receipt hashes and only over the separately agreed private transfer mechanism. The repository never marks `private_file_transfer_authorized=true`.

## Retention

Default working retention is 10 days, bounded to a maximum of 30 days by the close-kit intake. A signed NDA/SOW may require a shorter retention or immediate deletion/return; the stricter obligation controls. Repository artifacts should remain metadata/receipt-only so ordinary repository retention never becomes customer-model retention.

## Processing / subprocess boundary

The acceptance carrier is intentionally backend-neutral. It does not launch a customer model, execute an untrusted harness, invoke a shell command, write to a payment processor, or touch private storage. A real delivery environment must separately sandbox and authorize those operations. The reproducible command is represented here by SHA-256 identity only.

## Customer evidence packet

The minimum acceptance packet contains:

1. AT1 original model SHA-256 + byte count;
2. AT2 distinct ablated/intervention SHA-256;
3. AT3 restored SHA-256 + byte count exactly matching AT1;
4. AT4 three distinct harness-run receipt SHA-256 values (baseline, ablation, restore);
5. AT5 report SHA-256, concise finding, and explicit limitations; and
6. AT6 delivery receipt binding all required artifact/run/report hashes.

A processor/payment reference is deliberately orthogonal. Its presence never changes AT1–AT6 and never records customer acceptance or recognized revenue.

## Incident / HOLD behavior

If a secret or customer model bytes are presented to the public carrier, do not persist or echo them; move the interaction to the owner-private process. If rollback is not byte-exact, stop delivery, preserve only safe hashes/receipts, and record `HOLD_AT3_ROLLBACK`. If the customer requests a broader intervention, stop and route to change-order review rather than silently expanding scope.
